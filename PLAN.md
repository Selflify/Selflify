# План работ по Selflify

## Цель

Собрать production-minded MVP приложения **Selflify**, которое:

- заменяет статический root portal на `sendsay.dev`;
- не использует базу данных;
- читает и изменяет файловую конфигурацию напрямую;
- управляет сайтами, деплоями и глобальными настройками текущей preview-платформы;
- встраивается в уже существующую связку `Caddy + Cloudflare + /var/www`.

## Текущее состояние проекта

Сейчас в репозитории есть только инфраструктурная основа:

- `sites.json` как главный источник конфигурации;
- bash-скрипты генерации `Caddyfile` и root portal;
- cleanup-скрипт для старых preview;
- Docker-окружение только для `Caddy`;
- нет Next.js-приложения, UI, слоя авторизации и серверного API.

Это означает, что MVP нужно делать практически с нуля, с одноразовой миграцией от текущей реализации, но без runtime-fallback к старому формату.

## Рабочие допущения для MVP

Если до старта не будет других решений, предлагается исходить из следующего:

- Selflify разворачивается как отдельный сервис рядом с `Caddy`.
- `Caddy` продолжает обслуживать preview-домены и stable-домены как сейчас.
- `sendsay.dev` начинает проксироваться на Selflify вместо отдачи статического `index.html`.
- Основной источник правды для сайтов остаётся файловым.
- Все критичные изменения конфигурации сохраняются атомарно и проходят валидацию.
- Разрушающие действия вроде удаления deploy и сайта требуют явного подтверждения в UI, но сохранённые конфиги применяются автоматически.

## Зафиксированные решения

- Admin credentials панели хранятся в файле.
- Глобальные секреты и системные настройки, включая `Cloudflare API token`, также хранятся в файле.
- `selflify.config.json` становится единственным source of truth для глобальных настроек и списка сайтов.
- Первая версия должна уметь создавать, удалять и редактировать сайты.
- Изменения после сохранения применяются автоматически.
- Удаление deploy безвозвратное.
- Удаление сайта удаляет запись из конфига и DNS-записи, а файловая директория переносится в orphan storage для последующего cleanup.
- При создании сайта Selflify автоматически создаёт DNS-записи в Cloudflare.
- При создании сайта Selflify автоматически создаёт директорию сайта, директорию main branch и placeholder `index.html`.
- `sendsay.dev` проксируется на Selflify, а preview/stable-маршрутизация остаётся на стороне `Caddy`.
- Авторизация панели реализуется через `next-auth`.
- Вся инфраструктура Selflify разворачивается в одном production `docker-compose` вместе с `Caddy`.
- Для локальной разработки нужен отдельный `docker-compose.dev`.
- Основная UI-библиотека приложения: `Chakra UI`.
- Ввод логина и пароля для site preview auth делается через UI, а hash генерируется под капотом командой `caddy hash-password`.
- Нужен кастомный favicon в стилистике Netlify с адаптацией под палитру вокруг `#a12141`.
- Приложение должно запускаться локально в dev-режиме без Docker production-обвязки.
- Применение `Caddy`-конфига должно происходить через zero-downtime reload, а не через полный restart контейнера.
- Для hash/validate/reload Selflify должен иметь доступ к бинарю `caddy`, а сам `Caddy` должен быть доступен по internal admin endpoint внутри compose-сети.
- Старые конфиги, bash-генераторы и старый root portal не поддерживаются в целевой runtime-схеме.

## Рекомендуемые архитектурные ответы

### 1. Apply pipeline

Для всех mutating-операций используется единый pipeline:

1. Захватить глобальный operation lock.
2. Проверить `config_revision` и отклонить устаревшие формы.
3. Провалидировать и нормализовать входные данные.
4. Сгенерировать целевое состояние в temp-директории:
   - `selflify.config.json`
   - `Caddyfile`
5. Провалидировать `Caddyfile` локально через `caddy validate` или `caddy adapt`.
6. Выполнить подготовительные операции файловой системы:
   - создать директории сайта;
   - записать placeholder `index.html`;
   - при удалении сайта переместить директорию в orphan storage.
7. Атомарно записать live-конфиги и создать backup предыдущей ревизии.
8. Применить `Caddy` через zero-downtime reload.
9. Выполнить Cloudflare DNS-операции.
10. Сохранить итоговый статус операции:
   - `success`
   - `partial`
   - `failed`

Компенсации:

- если не прошла файловая или конфигурационная валидация, live-состояние не меняется;
- если не прошёл `Caddy reload`, откатываются конфиги из backup и повторно применяется последняя рабочая конфигурация;
- если не прошли DNS-операции, локальная конфигурация не откатывается, но операция получает статус `partial` с возможностью retry из UI.

### 2. Граница авторизации

- `sendsay.dev` обслуживается только Selflify и не защищается `basic auth` на уровне `Caddy`;
- вход в админку идёт только через `next-auth`;
- никакой legacy root auth в runtime не сохраняется;
- root portal целиком заменяется приложением Selflify.

### 3. Блокировки и консистентность

- Все mutating-операции сериализуются через global operation queue.
- Дополнительно используется файловый lock, чтобы защититься от повторного запуска процесса.
- Каждое успешное изменение увеличивает `config_revision`.
- Формы редактирования отправляют ожидаемую ревизию и получают conflict-ошибку, если конфиг уже изменился.

### 4. Security model

- `selflify.config.json` хранится с правами `0600`.
- backup-файлы конфигов имеют те же права доступа и ограниченный retention.
- `Cloudflare API token`, session secret и password hashes никогда не возвращаются в UI целиком.
- Логи не должны печатать секреты и сырые shell-команды с чувствительными аргументами.
- `Caddy` Admin API доступен только внутри docker network и не публикуется наружу.

### 5. Удаление сайта

- Удаление сайта не делает `rm -rf` директории сайта сразу.
- Вместо этого директория переносится в `/var/www/.orphaned-sites/<site>-<timestamp>`.
- Сайт удаляется из `selflify.config.json` и его DNS-записи удаляются из Cloudflare.
- Отдельный orphan-cleanup job удаляет такие директории спустя TTL, например 30 дней.

### 6. Инварианты конфигурации

- `site slug`:
  - только lowercase letters, digits and `-`;
  - regex: `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`;
  - уникален в рамках инсталляции;
  - `root` зарезервирован.
- `main_branch`:
  - нормализованный env name;
  - regex: `^[a-z0-9](?:[a-z0-9-]{0,62})$`.
- `dir` не редактируется произвольно в UI:
  - в MVP он вычисляется как `/var/www/<site-slug>`;
  - это убирает path traversal и конфликты путей.

### 7. Производительность

- Размеры сайтов и deploy не считаются полным `du` на каждый page load.
- Вводится cache layer для stats с TTL, например 60-120 секунд.
- Dashboard и site pages показывают cached value и timestamp последнего пересчёта.
- После mutating-операций кэш соответствующего сайта инвалидируется.
- В UI есть ручной refresh для принудительного пересчёта.

### 8. Local dev mode

- Локальный `npm run dev` работает только с fixture paths, а не с production `/var/www`.
- В dev используется отдельный `.dev/` или `/tmp/selflify-dev/` root.
- Cloudflare интеграция в dev заменяется на mock adapter.
- `Caddy reload` в dev не выполняется; вместо этого делается только локальная валидация генерируемого `Caddyfile`.

### 9. Граница ответственности v1

- V1 не управляет CI/CD пайплайнами и не запускает деплой сборок.
- GitHub Actions и `rsync` остаются внешней системой.
- Selflify отвечает за конфигурацию, DNS, просмотр deploy, удаление deploy и применение инфраструктурных настроек.
- Старые bash-генераторы и статический root portal выводятся из runtime-схемы и не поддерживаются.

### 10. Целевое окружение

- Production target: Linux-host с docker compose, shared volumes и доступом к `/var/www`.
- Local development: macOS/Linux с переназначаемыми путями через env.
- Single-instance deployment only для MVP.
- Расчётная нагрузка MVP:
  - до 50 сайтов;
  - до 200 deploy на сайт;
  - до 1 TB суммарных данных.
- Публичный API и webhook-автоматизация выносятся за пределы v1.

## Этапы работ

### 1. Уточнение архитектуры и фиксация контракта конфигурации

Задачи:

- зафиксировать структуру единого `selflify.config.json` для admin credentials, `server IP`, `domain`, `Cloudflare API token`, session secret, списка сайтов и служебных флагов;
- описать одноразовую миграцию с `sites.json` на `selflify.config.json` без последующей поддержки старого формата;
- описать контракт автоматического применения изменений после сохранения;
- зафиксировать список shell-операций, которые Selflify может выполнять без дополнительного ручного шага;
- описать схему zero-downtime reload для `Caddy` в рамках одного `docker-compose`.

Результат этапа:

- утверждённая схема конфигов;
- список разрешённых файловых и shell-операций;
- описание deployment topology.

### 2. Инициализация приложения

## Технические deliverables MVP

- Next.js приложение на App Router + TypeScript.
- UI на `Chakra UI`.
- Service layer для конфигов, файловой системы и shell-операций.
- Operation manager с lock, revision control и apply statuses.
- Единый `selflify.config.json` как source of truth.
- Setup/login flow для единственного администратора.
- Dashboard, Sites, Site Details, Settings.
- Dockerfile, production `docker-compose` и `docker-compose.dev`.
- Документация по деплою и миграции.

## Основные риски

- Потенциально опасные shell-операции на боевом сервере.
- Стоимость операций `du` и обхода директорий при большом количестве деплоев.
- Риск сгенерировать и применить невалидный `Caddyfile`.
- Автоматическое применение изменений повышает требования к валидации, блокировкам и rollback-стратегии.
- CRUD по сайтам увеличивает количество edge-cases: пустые директории, отсутствующий DNS, конфликтующие имена и права доступа.
- Автоматическая работа с Cloudflare DNS требует аккуратной обработки частично успешных операций.
- Использование `caddy hash-password` и reload-механизма требует продуманного доступа к бинарю `caddy` и/или Admin API из Selflify.

## Закрытые допущения для старта

1. MVP проектируется под нагрузку до 50 сайтов, до 200 deploy на сайт и до 1 TB суммарных данных.
2. Production поддерживается только на Linux; локальный dev поддерживается на macOS/Linux через fixture paths и env overrides.
3. Публичный API и webhook-слой исключаются из v1; CI/CD остаётся внешней системой.

## Рекомендуемый порядок запуска разработки

1. Сначала формализовать `selflify.config.json`, operation manager и apply pipeline.
2. Затем зафиксировать схему интеграции с `Caddy`, Cloudflare и orphan-cleanup.
3. После этого начинать реализацию service layer и auth.
4. UI-слой и страницы делать уже поверх согласованного backend-контракта.
